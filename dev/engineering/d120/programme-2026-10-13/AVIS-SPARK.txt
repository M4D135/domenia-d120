# 1) 15 priorités qui apporteraient le plus

## 1. Réconciliation stricte dashboard / résultats / base locale [E]

C’est la priorité numéro un.

Le symptôme “plus de postes au dashboard qu’en résultats même OU” est un signal rouge. Il faut rendre impossible, par conception, qu’un widget affiche un nombre qui ne correspond pas à la liste ouverte.

Actions concrètes :

- Chaque widget doit être adossé à une “vue canonique” :
  - périmètre OU,
  - filtres,
  - statut inclus/exclu,
  - fraîcheur autorisée,
  - epoch/génération,
  - liste GUID exacte ou requête canonique déterministe.
- Le clic sur un widget doit ouvrir la liste des GUID exacts, pas une nouvelle approximation.
- Ajouter un panneau “Réconciliation” :
  - nombre dashboard,
  - nombre liste,
  - nombre distinct GUID dans SQLite,
  - nombre attendu par filtre AD,
  - écart,
  - motif possible : tombstone, disabled, OU moved, stale, partial, auth, timeout, cross-epoch.
- Interdire visuellement toute comparaison entre epoch différentes.
- Conserver les collectes anciennes, mais ne jamais les mélanger dans une vue active.

Condition d’acceptation :

- Sur une OU donnée, dashboard et liste doivent avoir le même nombre de GUID distincts.
- Écart toléré : 0.
- Si écart, le diagnostic doit afficher la cause ou “cause inconnue”, jamais un nombre silencieux.

## 2. Freshness / santé par champ et par source, pas par machine globale [E]

Le vieillissement AD/ping/WMI mélangé est un problème de modèle, pas seulement d’UI.

Actions concrètes :

- Ne pas avoir un seul statut “machine saine”.
- Avoir des statuts par famille :
  - AD,
  - Ping,
  - WMI/CIM,
  - Console,
  - Inventaire,
  - Probe,
  - Admin action.
- Puis descendre par champ :
  - `ad.lastLogonTimestamp`,
  - `ad.whenChanged`,
  - `wmi.osVersion`,
  - `wmi.biosVersion`,
  - `ping.icmp`,
  - `tcp.445`,
  - `ldap.ping`,
  - `console.session`,
  - `software.registry`,
  - `hardware.support`.
- Pour chaque champ affiché :
  - source,
  - date de dernière réussite,
  - date de dernière tentative,
  - âge,
  - erreur,
  - fraîcheur,
  - confiance.
- “Inconnu” doit rester distinct de “sain”.
- Un timeout n’est pas une preuve d’inaccessibilité.
- Un champ absent peut être :
  - non collecté,
  - non supporté,
  - interdit par droits,
  - bloqué réseau,
  - erreur WMI,
  - erreur AD,
  - objet tombstone,
  - machine éteinte,
  - inconnu.

Condition d’acceptation :

- 100 % des champs affichés doivent avoir provenance, âge et statut.
- Aucun timeout ne doit être affiché comme “AD inaccessible” sans distinction.
- “Inconnu” ne doit jamais être coloré comme “sain”.

## 3. Auth sérialisée, anti-verrouillage, aucun fallback automatique [Q]

La protection auth partagée existe déjà dans le contexte. Il faut la qualifier sérieusement, pas la réinventer.

Actions concrètes :

- Une seule tentative d’authentification par compte/domaine à la fois.
- File d’attente pour les demandes concurrentes.
- Aucun fallback automatique après erreur auth.
- Aucun contournement par compte alternatif automatique.
- Pause de l’identité après erreur sensible.
- Cooldown local.
- UI explicite :
  - “Authentification en cours”,
  - “Identité en pause”,
  - “Nouvelle tentative manuelle requise”.
- Journal local :
  - compte,
  - domaine,
  - usage,
  - résultat,
  - pas de mot de passe,
  - pas de token,
  - pas de secret.
- Métriques :
  - nombre de tentatives,
  - erreurs auth,
  - erreurs réseau,
  - erreurs permission,
  - erreurs timeout.

Condition d’acceptation :

- 10 déclenchements concurrents sur la même identité doivent produire une seule tentative auth.
- Aucun fallback automatique.
- Aucun mot de passe dans les logs.
- En simulation, aucune boucle de retry susceptible de provoquer un verrouillage.

## 4. Favori OU : ouvrir le chemin, sélectionner l’OU, charger la liste [E]

C’est un quick win important pour la perception de fiabilité.

Actions concrètes :

- Un favori OU doit stocker :
  - domaine,
  - chemin DN complet,
  - GUID OU si disponible,
  - filtre associé,
  - vue associée.
- Au clic :
  - l’arbre OU se déplie jusqu’au chemin,
  - l’OU est sélectionnée,
  - le breadcrumb est à jour,
  - la liste est chargée,
  - le dashboard associé est rafraîchi si pertinent.
- Si l’OU n’existe plus :
  - afficher “favori invalide”,
  - ne pas charger une liste silencieuse.

Condition d’acceptation :

- Clic favori :
  - arbre ouvert,
  - OU sélectionnée,
  - breadcrumb cohérent,
  - liste chargée.
- Sur cache local, ouverture < 500 ms.
- Sur liste locale 5000 objets, chargement < 2 s, à valider sur Windows.

## 6. Atelier de requêtes : simplifier sans appauvrir [E]

L’atelier existe déjà en 3 étapes avec modèles, champs, coûts, sources, dates. Il faut le rendre moins confus.

Actions concrètes :

- Garder 3 étapes claires :
  1. Périmètre : OU, domaine, statut, fraîcheur.
  2. Critères : champs typés, opérateurs, valeurs.
  3. Aperçu : nombre estimé, colonnes, coût, source, date, export.
- Ajouter des “missions” prêtes à l’emploi :
  - postes sans WMI,
  - postes sans patch récent,
  - postes éteints suspects,
  - OU à migrer,
  - comptes inactifs,
  - postes sans inventaire logiciel,
  - postes avec erreur auth,
  - postes avec timeout réseau.
- Afficher clairement :
  - source AD/WMI/Ping,
  - coût estimé,
  - fraîcheur,
  - droits nécessaires,
  - champs non supportés.
- Interdire le SQL brut par défaut.
- Proposer un mode avancé séparé, non par défaut.
- Permettre de sauvegarder une recherche comme dashboard partagé localement.

Condition d’acceptation :

- Un utilisateur peut créer une requête utile en 3 étapes.
- Il voit le nombre estimé avant exécution.
- Il voit la source, le coût et la fraîcheur.
- Aucune requête brute n’est nécessaire pour les cas courants.

## 7. Ordonnanceur de collecte par OU choisie, incrémental, groupé, backpressure [E]

Le pipeline central existe. Il faut le qualifier et l’orienter “réseau lent”.

Actions concrètes :

- Par défaut :
  - OU choisie,
  - jamais scan domaine complet.
- Regrouper par :
  - classe AD,
  - attributs AD,
  - classe WMI,
  - session CIM,
  - sous-réseau pour ping,
  - DC pour LDAP.
- Ajouter une politique de fraîcheur :
  - AD : 1 h,
  - Ping : 5 min,
  - WMI : 24 h,
  - Inventaire logiciel : 7 j,
  - Matériel : 30 j,
  - Console : on demand ou court terme.
- Collecter uniquement les champs périmés.
- Utiliser des deltas si pertinent :
  - `whenChanged`,
  - `uSNChanged`,
  - comparaison avec epoch précédente.
- Circuit breaker par :
  - DC,
  - sous-réseau,
  - compte,
  - source.
- Backpressure :
  - file bornée,
  - fusion des jobs obsolètes,
  - priorité à la vue active,
  - abandon des jobs anciens non pertinents.
- Max :
  - objets par job,
  - durée par job,
  - parallélisme,
  - débit réseau.

Condition d’acceptation :

- Aucun scan domaine complet par défaut.
- File bornée.
- Pas de saturation UI.
- Pas de retry storm.
- Une collecte en arrière-plan ne doit pas empêcher la navigation.

## 9. Sondes AD/WMI sûres, support-aware, sans effets de bord [E]

C’est critique pour un outil professionnel.

Actions concrètes :

- Ne jamais utiliser `Win32_Product` dans un inventaire de routine.
- Pour le logiciel, préférer :
  - clés de désinstallation registre,
  - MSIX/Appx si pertinent,
  - versions de fichiers,
  - sources locales déjà présentes,
  - inventaire existant si disponible, sans agent permanent.
- Pour le matériel :
  - classes WMI/CIM supportées,
  - matrice de support par OS/fournisseur,
  - “inconnu” si non supporté.
- Pour les patches :
  - prudence,
  - source,
  - âge,
  - coût,
  - erreurs.
- Pour les sessions :
  - on demand,
  - pas en boucle permanente.
- Pour les services :
  - optionnel,
  - coûteux,
  - filtré.
- Pour les disques/SMART :
  - seulement si supporté,
  - sinon inconnu.

Condition d’acceptation :

- 0 appel `Win32_Product` dans les collectes de routine.
- Aucun effet de bord MSI connu.
- Tout champ matériel non supporté est marqué “inconnu”, pas “absent” ni “sain”.

## 10. Présence multi-signal : ping bloqué != offline [E]

Le ping seul est dangereux.

Actions concrètes :

- Signaux de présence :
  - résolution DNS,
  - ICMP,
  - TCP 445,
  - TCP 3389,
  - TCP 135,
  - TCP 5985/5986 si WinRM,
  - LDAP ping,
  - SMB,
  - RDP,
  - WMI/CIM,
  - console,
  - activité AD récente,
  - `lastLogonTimestamp` approximation.
- États :
  - `online`,
  - `reachable_partiel`,
  - `offline_suspect`,
  - `unknown`,
  - `stale`,
  - `auth_error`,
  - `network_blocked`,
  - `permission_error`.
- Ne jamais conclure “offline” sur un simple timeout ICMP.
- Afficher les signaux utilisés.

Condition d’acceptation :

- Un timeout ICMP seul ne doit jamais produire “offline”.
- Un état “offline_suspect” doit reposer sur plusieurs signaux négatifs ou une règle explicite.
- L’utilisateur voit pourquoi la machine est considérée comme éteinte ou injoignable.

## Idée 2 : “Consensus de présence multi-signal”

Le ping seul est un piège.

Concept :

- Chaque machine a un état de présence calculé par consensus.
- Signaux :
  - DNS résolu,
  - ICMP,
  - TCP 445,
  - TCP 3389,
  - TCP 135,
  - TCP 5985/5986,
  - LDAP ping,
  - SMB,
  - RDP,
  - WMI/CIM,
  - console,
  - activité AD récente,
  - `lastLogonTimestamp` approximation.

États :

- `online`
- `reachable_partiel`
- `offline_suspect`
- `unknown`
- `stale`
- `auth_error`
- `network_blocked`
- `permission_error`

Règle :

- Un timeout ICMP seul ne produit jamais `offline_suspect`.
- `offline_suspect` nécessite plusieurs signaux négatifs ou une règle explicite.
- L’UI affiche les signaux utilisés :
  - “DNS OK, ICMP timeout, TCP 445 timeout, WMI auth error”.

Pourquoi c’est fort :

- Cela évite les faux éteints.
- Cela rend le dashboard crédible.
- Cela correspond à la réalité des réseaux entreprise.

Acceptation :

- Aucun offline basé uniquement sur ping.
- Chaque état affiche ses signaux.

# Pièges techniques à intégrer explicitement dans le produit

## 1. `Win32_Product` : danger d’effets de bord

`Win32_Product` ne doit pas être utilisé comme source d’inventaire de routine.

Pourquoi :

- Son énumération peut déclencher des comportements MSI.
- Elle peut être lente.
- Elle peut provoquer des effets de bord sur des installations MSI.
- Elle est mal adaptée à un inventaire massif sur 5000 postes.

À faire :

- Éviter `Win32_Product` dans les collectes automatiques.
- Préférer :
  - clés de désinstallation registre,
  - MSIX/Appx si pertinent,
  - versions de fichiers,
  - sources locales déjà présentes,
  - inventaire existant sans agent permanent.
- Si un besoin MSI spécifique existe :
  - le traiter séparément,
  - avec avertissement,
  - coût,
  - scope,
  - audit.

---

## 2. Ping bloqué != machine offline

Un timeout ICMP ne prouve pas que la machine est éteinte.

Pourquoi :

- ICMP peut être bloqué par firewall.
- EDR/antivirus peut bloquer.
- VLAN peut filtrer.
- WAN/VPN peut filtrer.
- La machine peut être allumée mais injoignable par ping.

À faire :

- Utiliser plusieurs signaux :
  - DNS,
  - TCP 445,
  - TCP 3389,
  - TCP 135,
  - TCP 5985/5986,
  - LDAP ping,
  - SMB,
  - RDP,
  - WMI/CIM,
  - console,
  - activité AD récente.
- Afficher l’état :
  - `reachable_partiel`,
  - `network_blocked`,
  - `offline_suspect`,
  - `unknown`.

---

## 3. `lastLogon` non répliqué et `lastLogonTimestamp` approximatif

Deux champs AD sont souvent mal compris.

`lastLogon` :

- Non répliqué.
- Valeur par DC.
- Un DC peut voir un logon que les autres ne voient pas.
- À utiliser avec prudence.
- Si affiché, dire que c’est une valeur DC locale.

`lastLogonTimestamp` :

- Répliqué.
- Mais approximatif.
- Pas un temps réel.
- Granularité potentiellement de plusieurs jours selon configuration/implémentation.
- À afficher comme approximation.

À faire :

- Ne jamais présenter `lastLogonTimestamp` comme “dernière connexion exacte”.
- Afficher :
  - “approximation”,
  - “source AD”,
  - “âge”,
  - “peut être décalé”.
- Si besoin de précision, prévoir une option explicite “lire `lastLogon` sur DC ciblé”, avec avertissement.

---

## 4. Matériel sans support : ne pas deviner

Le matériel peut être :

- non reconnu,
- non supporté par WMI/CIM,
- partiellement exposé,
- virtuel,
- custom,
- exotique,
- bloqué par droits,
- bloqué par firewall.

À faire :

- Ne pas mettre “absent” si c’est “inconnu”.
- Ne pas mettre “sain” si c’est “non supporté”.
- Afficher :
  - `unsupported`,
  - `unknown`,
  - `partial`,
  - `permission_error`,
  - `network_blocked`.
- Maintenir une matrice de support par classe WMI/CIM et par OS/fournisseur.

---

## 5. Dates, inconnus, clock skew

Les dates sont un terrain de faux diagnostics.

Pièges :

- Dates futures.
- Clock skew.
- UTC vs local.
- Timezone.
- Dernier succès ancien mais affiché comme récent.
- Dernière tentative récente mais sans succès.
- `lastLogonTimestamp` mal interprété.
- Date AD vs date WMI vs date ping mélangées.

À faire :

- Stocker en UTC.
- Afficher en local.
- Séparer :
  - `lastSuccess`,
  - `lastAttempt`,
  - `age`,
  - `error`.
- Signaler les dates futures suspectes.
- Signaler le clock skew si détecté.
- Ne jamais mélanger les horodatages de sources différentes sans provenance.

# Avis final

Domenia a déjà une base sérieuse : pipeline central, SQLite locale, GUID + domaine, epoch/path/generation, backpressure, auth protégée, atelier 3 étapes, dashboards, sondes. Le vrai saut professionnel n’est pas d’ajouter une base distante, un agent, du cloud ou une réécriture. Le saut est de rendre le système auto-explicable.

La règle centrale devrait être :

> Toute donnée affichée doit avoir une source, une fraîcheur, un état, une erreur possible, et doit pouvoir être réconciliée avec la liste exacte.

Si Domenia arrive à garantir cela, il devient un outil professionnel fiable. S’il ne le garantit pas, chaque incident “dashboard ≠ résultats”, “timeout = inaccessible”, “ping = offline”, “auth parallèle = verrouillage” continuera d’user la confiance.
