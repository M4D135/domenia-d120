## Adaptations V2 et limites

Le produit utilise des assemblages C# compilés et une interface WebView2. Les objets WPF `ResultRow`, l’analyse/import
de scripts, les compilations Add-Type, ISE et les plans XAML ne sont pas réintroduits. Les déclarations sont compilées
dans chaque assemblage propriétaire : ajout ou retrait d’un export exige une mise à jour de cette déclaration.
Le plan enregistre des opérations ; il ne lance aucune authentification ni opération métier.

Les empreintes vérifient tous les octets du pack. Une normalisation des fins de ligne affaiblirait ce contrat ; les fichiers
modifiés restent refusés. Le plafond D1 de 250 fichiers ne convient pas aux runtimes privés du pack V2 : la borne existante
de 4096 est conservée et annoncée. Aucun format de manifeste ou de données utilisateur ne change.

WinVerifyTrust utilise `WTD_UI_NONE`, `WTD_CACHE_ONLY_URL_RETRIEVAL` et `WTD_REVOCATION_CHECK_NONE` ; l’état natif est
toujours fermé. Un succès est une validation par la politique Windows locale, sans contrôle de révocation en ligne.
`TRUST_E_NOSIGNATURE` est autorisé avec mention explicite : les packs actuels ne possèdent pas de certificat éditeur.
Tout autre refus est bloquant. Ces règles suivent la [documentation Microsoft de WINTRUST_DATA](https://learn.microsoft.com/en-us/windows/win32/api/wintrust/ns-wintrust-wintrust_data).
Le précontrôle WebView2 lit sa version sans créer de profil ni de contrôle, via
[GetAvailableBrowserVersionString](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2environment.getavailablebrowserversionstring).

Les traces avant admission ne chargent pas le journal applicatif et ne conservent pas les arguments de commande. Un
message pouvant contenir un secret est omis en entier. Les racines sont locales ; aucune trace n’est écrite dans le pack.
Une défaillance native ou CLR avant l’entrée dans Main reste hors de portée du diagnostic C#.

La politique de premier plan n’utilise ni hook global, ni boucle, ni TopMost. Le retour d’une session verrouillée ne relance
pas une activation. La fenêtre distincte d’affichage d’un secret garde son contrat existant ; elle n’est pas la fenêtre
principale ni la connexion. Les appels WinForms et SystemEvents nécessitent encore une recette visuelle ultérieure ;
la politique de décision est couverte par tests Windows, sans prétendre constituer une recette VM.

## Vérifications écrites

- `RuntimePlanTests` : graphe invalide sans constructeur, vrais exports dans les deux modes, origine et bibliothèques
  chargées, doublon réel dans un processus neuf ; `PlatformTests` compare également le catalogue existant.
- `StartupBoundaryTests` : activation unique, départ de session, logs relus après rotation/refus, masquage, politique
  signature, racines absolues et disposition wad.
- `PackageIntegrityTests` : données hors code, altération CRLF/LF, plafond, marqueurs valides/invalides, chemin réel check-only.
- `SearchOperationsTests` : chaque événement moteur porte le plan confirmé. `rechercher-reconcile.test.mjs` : vraie grille,
  anciennes réponses ignorées, historique immuable, filtres recalculés et DOM/focus inchangés hors lignes modifiées.

l’identité du bootstrap et remplacé deux recherches quadratiques dans le marquage des cibles par un ensemble indexé.
