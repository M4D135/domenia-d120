## Identité et reconstruction

`wad/package-contract.json` et `wad/contracts/` font partie du manifeste tenu.
L’étiquette est `AAAA.MM.JJ-DOMENIA-version-CANDIDATE-empreinte64`. La date vient du
commit, jamais d’un texte de fenêtre. PROD et DEV partagent la même identité ;
leurs empreintes globales diffèrent puisque le DEV ajoute les sources. Le registre
livré doit aussi être identique à celui des sources DEV.

`tools/compare-rebuild.py <livré> <reconstruit> --report <rapport-neuf>` ne lance
aucun binaire. Il conserve tous les rapports précédents et nomme chaque écart,
y compris celui des preuves d’environnement horodatées. Une égalité prouve des
octets égaux, jamais des tests Windows, une recette domaine ou la confiance dans
l’éditeur. Aucun rebuild réel n’est annoncé dans ce lot. Les runtimes privés ont
leur propre inventaire ; Domenia.Simulation reste une capacité du produit.

## Registre des opérations

Les corps V2 partagent des dépendances compilées : les onze noms D1 référencent
la même fermeture des huit couches V2, comprenant sources, projets et paramètres
de build. Cette adaptation évite de prétendre qu’un corps isolé couvre ses appels.
Le registre est mis à jour explicitement après revue avec
`tools/update-operation-contracts.py --write`. Une compilation vérifie uniquement :
aucune mise à jour automatique des épingles. Les ajouts, suppressions et modifications
de sources changent le contrat. Le manifeste tient ensuite les binaires livrés.
Ces contrôles établissent une cohérence, pas une signature d’éditeur du pack.

## Confiance de l’éditeur

Politique facultative, lue seulement dans
`HKLM\Software\Policies\Domenia\Publisher` (vue 64 bits) :
`CertificateSha256` est un REG_MULTI_SZ de seize empreintes SHA-256 du certificat
DER au maximum ; `RequirePinnedPublisher` est un DWORD 0 ou 1. Aucun réglage HKCU,
JSON du pack, sujet ou nom de certificat ne devient une autorité. Politique
illisible ou invalide : refus explicite. Une politique obligatoire sans épingle
valide n’est jamais remplacée par une permission implicite.

Sans politique, un EXE non signé reste indiqué non signé, éditeur non certifié.
Une signature Windows valide sans épingle reste sans confiance éditeur établie.
La vérification locale utilise le cache Windows sans interrogation de révocation
sur Internet. Le verdict Authenticode concerne **l’EXE détenu uniquement** : les
SHA-256 du manifeste mutable ne signent pas les DLL, ressources ou scripts.
La nouvelle copie activée et les restaurations repassent la politique en vigueur.

## Désinstallation et limites volontaires

Depuis un autre pack vérifié, aperçu puis confirmation :
`livraison apercu-desinstallation <cible> local=supprimer profil=conserver`, puis
`livraison desinstaller <cible> <confirmation> local=supprimer profil=conserver`.
Les deux choix sont fournis ensemble ; sans choix, les données restent intactes.
Le profil vient de Windows, jamais d’un chemin saisi dans les arguments.

La suppression est bornée à 8 192 fichiers et 8 Gio ; la preuve est elle-même bornée
à 8 192 entrées, dossiers compris, 32 niveaux et un inventaire JSON de 1 Mio.
Un écrivain actif, une jonction,
un fichier substitué ou une confirmation devenue obsolète empêche le retrait.
Les fichiers modifiés après interruption sont conservés et nommés. Aucun dossier
n’est effacé récursivement ; coffre Windows, sauvegardes de code et preuves restent
conservés. Le verrou `.lifecycle.lock` est volontairement gardé : le retirer après
fermeture pourrait supprimer un substitut concurrent. Ces deux conservations
remplacent explicitement les demandes D1 de suppression globale et du verrou.
