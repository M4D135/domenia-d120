# Configuration distribuable : service, premier démarrage et UI

Demandes explicites de David du 25 octobre 2026 : export/import, application initiale, proposition lors du premier lancement d’une nouvelle version, puis bouton « Définir comme configuration par défaut » depuis la PROD configurée. Ce lot raccorde le codec/CLI déjà compilé dans 117 aux vrais consommateurs. Il ne promeut aucun statut de catalogue sur seule compilation.

Le module `ConfigurationOperations` expose les vrais choix portables, l’export exact sélectionné, l’aperçu et l’import atomique. La liste est l’allowlist `PreferenceApproval` entière plus l’interface validée. OU opt-in ; quatre groupes sans OU utilisent leur défaut effectif lorsqu’absents. Les clés non choisies et les données futures de destination restent conservées. Les propriétés inconnues à l’intérieur d’une valeur exportée sont refusées pour éviter d’embarquer une charge étrangère sous un nom approuvé.

`FilePreferenceStore.Configuration` lit une seule fois les octets qualifiés/bornés, les parse avec le même lecteur strict que les migrations, prend le mutex interprocessus et la gate locale, refuse les changements en attente, valide le jeton du document entier et la source après mutex. La sauvegarde CreateNew est flushée, relue sur le même handle, et comparée par longueur/SHA avant le remplacement atomique. Un échec laisse l’ancien choix en mémoire et sur disque ; une sauvegarde déjà créée reste conservée. Les décisions build+SHA et les réglages sont écrits dans le même document. 128 décisions au plus ; la saturation refuse d’effacer l’historique pour faire de la place.

`ConfigurationSeedCoordinator` refuse simulation et sessions non habilitées avant acquisition. `Composition` initialise le seed avant création des modules/restauration des préférences et avant WebView. Profil moteur absent ET profil WebView absent : application automatique conditionnelle. Sinon : proposition serveur. Application/refus exigent source SHA et jeton du dernier aperçu ; une source remplacée pendant l’attente est refusée. Absence réelle et document inaccessible/corrompu/futur sont distingués.

La page « Configuration à diffuser » affiche inclus/exclus, sélection d’OU, aperçu exact, export/import et le bouton demandé. Le bouton pack appelle `settings.defaults.package {text}` livré par root ; il attend son résultat et respecte l’annulation. Les réglages d’interface importés sont identifiés et appliqués une seule fois par profil web, après succès serveur. Les réglages métier demandent un redémarrage ; aucun changement de source/compte ni accès AD/SMB n’est déclenché par le service.

Tests écrits : sept C# dans `ConfigurationSeedTests` (profil vierge, profil web existant, décisions/version/SHA, backup exact, CAS, source tardive, document futur, échec physique, vrais handlers simulation), un test de reçus partiels/contradictoires dans `ConfigurationDecisionTests`, quatre tests DOM dans `configuration-defaults.test.mjs` (sélection OU/pack/annulation, proposition et refus, interface une fois, callback tardif). Les quatre tests codec de 117 restent conservés. Aucun test/build exécuté localement ; validation VM orchestrée par root uniquement.

Limites explicites : ce format porte les préférences approuvées et l’interface, pas `Domenia.config.json` (règles administrateur distinctes du pack), les dispositions complètes ni les bibliothèques. Ces dernières gardent leurs formats dédiés. L’ancien export/import de préférences reste disponible ; le nouveau parcours est celui avec backup et commit atomique complet. La copie de pack/ZIP et son manifeste relèvent du lot root `PackageDefaults`, sans réécriture du pack en cours. Le scénario multi-instance UI/host réel reste à confirmer dans les tests critiques Windows.
